# ТЗ для проекта E-Sukhum: API времени в пути с учётом пробок

**Заказчик API:** система «Социальное такси» (https://staxi.apsoftgroup.ru).
**Исполнитель:** проект E-Sukhum (`sukhum-transport`, API `https://api.e-sukhum.com`).
**Дата:** 10.11.2026.

## 1. Зачем это нужно

Диспетчер социального такси назначает поездку: «забрать в 09:00, быть на месте к 09:30».
Сейчас он может вписать любое время, и система не знает, успеет ли машина. Клиенты едут на
процедуры ко времени, машина часто везёт 2–3 человек попутно, а следующий заказ начинается
сразу после предыдущего — ошибка в оценке дороги ломает весь день.

У E-Sukhum уже есть то, чего нам не хватает: скорости по отрезкам улиц «сейчас» и «обычно в
этот час» (`traffic_state`, `traffic_edges_geo`, профиль по часам). Нам не нужны сами отрезки —
нужен готовый ответ на вопрос **«сколько ехать из А в Б, если выехать в такое-то время»**.

Как мы будем это использовать:

1. **В форме заказа.** Диспетчер вводит адреса и «быть на месте к 09:30» — система
   подсказывает «выезжать не позже 09:08, в пути около 17 мин (в это время обычно 14–22)».
   Если указанное время подачи не оставляет запаса — предупреждение (не запрет).
2. **По цепочке заказов машины.** Для каждой машины проверяем переезды между соседними
   заказами: «от поликлиники №1 до ул. Чанба, 8 ехать 12 мин, а между заказами 5 мин».
3. **Для водителя** — позже: ориентир «выезжать в 08:50».

Время посадки (коляска, сопровождающий) мы добавляем на своей стороне — от API нужно только
чистое время движения.

## 2. Что нужно от API

Три метода. Обязательны первые два; третий сильно упростит нам жизнь, потому что адреса у нас
хранятся текстом.

### 2.1. Время в пути — `POST /v1/routing/eta`

Запрос:

```json
{
  "from": { "lat": 43.0051, "lng": 41.0331 },
  "to":   { "address": "Сухум, ул. Аргун, 2" },
  "depart_at": "2026-11-11T09:00:00+03:00"
}
```

- `from` / `to` — либо координаты (`lat`, `lng`, WGS-84), либо `address` строкой (если есть
  геокодер, см. 2.3). Если адресного варианта не будет — только координаты, геокодирование
  сделаем сами.
- Время — одно из двух: `depart_at` (выезд в этот момент) **или** `arrive_by` (нужно приехать
  к этому моменту; тогда API подбирает время выезда). Без обоих — «выезд сейчас».
- Время может быть в будущем до 14 дней: заказы на завтра составляются накануне. Для
  будущего используется типичный профиль (день недели × время); для ближайшего часа — с
  учётом текущей обстановки.
- Профиль — легковой автомобиль/микроавтобус. Автобусные маршруты и остановки не нужны.

Ответ `200`:

```json
{
  "duration_s": 1020,
  "duration_low_s": 840,
  "duration_high_s": 1320,
  "duration_free_flow_s": 660,
  "distance_m": 6400,
  "depart_at": "2026-11-11T09:00:00+03:00",
  "arrive_at": "2026-11-11T09:17:00+03:00",
  "traffic_level": 2,
  "basis": "typical",
  "coverage": 0.86,
  "from": { "lat": 43.0051, "lng": 41.0331, "matched_address": null },
  "to":   { "lat": 43.0102, "lng": 41.0245, "matched_address": "Сухум, ул. Аргун, 2" },
  "data_as_of": "2026-11-10T22:10:00+03:00"
}
```

| Поле | Смысл |
|---|---|
| `duration_s` | ожидаемое время движения, секунды — главное число |
| `duration_low_s` / `duration_high_s` | разумный разброс (например, 20-й и 80-й перцентили); мы показываем диспетчеру «14–22 мин» и закладываем запас по верхней границе |
| `duration_free_flow_s` | время по пустой дороге — чтобы показать «из-за пробок +6 мин» |
| `distance_m` | длина маршрута |
| `depart_at` / `arrive_at` | оба момента всегда заполнены, каким бы ни был запрос |
| `traffic_level` | 1 свободно / 2 медленно / 3 пробка — в целом по маршруту (та же шкала, что в слое «Пробки») |
| `basis` | на чём основана оценка: `live` (текущие данные), `typical` (обычно в это время), `mixed`, `free_flow` (данных нет, посчитано по допустимой скорости) |
| `coverage` | доля длины маршрута, для которой были реальные данные о скорости, 0…1. При низком значении мы пометим оценку как грубую |
| `from` / `to` | к каким точкам привязались; для адресов — что именно распознано |
| `data_as_of` | свежесть данных о пробках |

Геометрия маршрута (`geometry`, GeoJSON LineString) — по запросу `"geometry": true`,
по умолчанию не нужна.

### 2.2. Пакетный расчёт — `POST /v1/routing/eta/batch`

Чтобы проверить расписание машины на день одним запросом.

```json
{
  "items": [
    { "id": "t1", "from": {…}, "to": {…}, "depart_at": "…" },
    { "id": "t2", "from": {…}, "to": {…}, "arrive_by": "…" }
  ]
}
```

- До 50 элементов в запросе; каждый — как тело из 2.1 плюс произвольный `id`.
- Ответ: `{ "items": [ { "id": "t1", …поля из 2.1… }, { "id": "t2", "error": { "code": "…" } } ] }` —
  ошибка в одном элементе не роняет остальные.

### 2.3. Геокодер — `GET /v1/geocode?q=Сухум, ул. Чанба, 8` (желательно)

Ответ: до 5 вариантов `{ "lat", "lng", "address", "kind": "house|street|place", "score" }`.
Нужны адреса Сухума (улица + дом) и известные места (больницы, поликлиники, бассейн).
Мы будем геокодировать адрес один раз при сохранении клиента или места и хранить координаты
у себя, так что нагрузка небольшая. Если геокодера в ближайших планах нет — напишите, сделаем
иначе; методы 2.1–2.2 тогда принимают только координаты.

## 3. Общие требования

- **Доступ:** ключ API в заголовке (`Authorization: Bearer …` или `X-Api-Key`). Вызываем только
  с нашего сервера (ключ не попадает в браузер и приложение), поэтому CORS не нужен.
- **Нагрузка:** маленькая. Оценка — до 2–3 тыс. расчётов в сутки, пики до 5 запросов в секунду
  (диспетчер печатает адрес; пакет при открытии доски дня). Геокодер — до 200 запросов в сутки.
- **Скорость ответа:** одиночный расчёт — до 500 мс (95-й перцентиль), пакет из 50 — до 3 с.
  Форма заказа ждёт ответа, пока диспетчер вводит данные.
- **Время:** ISO 8601 со смещением; если смещения нет — считать Europe/Moscow (UTC+3).
- **Зона:** обязательно Сухум и пригороды. Точки вне покрытия дорожного графа — не ошибка,
  если маршрут построить можно: считайте по допустимым скоростям и верните `basis: "free_flow"`
  и честный `coverage`. Машины ездят по всей Абхазии, межгородские поездки (Гагра, Гудаута,
  Очамчыра) нам тоже полезны хотя бы в таком виде.
- **Ошибки:** единый формат `{ "error": { "code": "…", "message": "…" } }`, коды:
  `invalid_request` (400), `unauthorized` (401), `address_not_found` (404 или элемент пакета),
  `no_route` (404), `out_of_coverage` (422, если маршрут построить нельзя вовсе),
  `rate_limited` (429, с `Retry-After`), `unavailable` (503).
- **Версия:** путь `/v1/…`; поля можно добавлять, существующие не менять и не удалять без `/v2`.
- **Сбой сервиса:** при 5xx или тайм-ауте мы молча работаем без подсказки, поэтому отдельного
  SLA не просим — но сообщите, если ожидаются регулярные окна пересчёта, когда API недоступно.
- **Персональные данные:** мы получаем только агрегат «время по маршруту», без отрезков и без
  идентификаторов машин, так что требование «не меньше 3 разных машин на участок» для этого
  метода, по нашему пониманию, не мешает. В запросах к вам уходят координаты или адреса
  клиентов без имён и диагнозов; просим не хранить их в логах дольше, чем нужно для отладки.

## 4. Что считается готовым

1. Методы 2.1 и 2.2 работают на `https://api.e-sukhum.com` по ключу, выданному для
   «Социального такси».
2. Для одного и того же маршрута по центру Сухума расчёт на будний день 09:00 заметно
   отличается от расчёта на 03:00 (то есть пробки действительно учитываются), а `basis` и
   `coverage` это объясняют.
3. Запрос с `arrive_by` возвращает такое `depart_at`, что `depart_at + duration_s = arrive_by`
   (с точностью до минуты).
4. Точность: на 20 контрольных поездках (мы пришлём фактические времена «клиент в машине» →
   «доставил» из нашей системы) фактическое время попадает в диапазон
   `duration_low_s…duration_high_s` не реже чем в 70% случаев. Цифру можно обсудить после
   первых замеров.
5. Короткое описание: адрес, пример запроса и ответа, как получить ключ, лимиты.

## 5. Вопросы к E-Sukhum

1. Есть ли уже маршрутизируемый дорожный граф (а не только отрезки со скоростями)? Если
   нет — нас устроит любой движок (OSRM/Valhalla с вашими скоростями, pgRouting), выбор за вами.
2. Насколько далеко вперёд осмысленен прогноз: профиль «день недели × час» или точнее
   (15 минут)? Учитываются ли праздники и погода?
3. Геокодер — в какие сроки и с каким покрытием домов?
4. Можно ли получить ещё и слой «пробки сейчас» (`/v1/traffic/now`) для показа на нашей карте
   диспетчера? Это не срочно и не блокирует основную задачу.
5. Со своей стороны можем отдавать вам обезличенные времена проезда наших машин (откуда,
   куда, когда, сколько ехали) — если они пригодятся для калибровки.

## 6. Что сделаем мы после появления API

Серверная функция-прослойка (ключ хранится у нас на сервере), координаты у клиентов и мест,
подсказка времени выезда и предупреждение «можно не успеть» в форме заказа, проверка цепочки
заказов машины на доске дня. Ограничений вводить не будем — только подсказки диспетчеру.
